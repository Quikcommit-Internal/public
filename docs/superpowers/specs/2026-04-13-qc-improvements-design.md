## Feature 1 — Richer Commit Bodies

### Goal
Commit messages generated by `qc` and `qc --push` should consistently include a body with bullet points when the diff has enough substance. Trivial changes (version bumps, typo fixes) stay as header-only.

### Substance heuristic

New helper in `packages/ai-worker/src/index.ts`:

```ts
function hasSufficientSubstance(diff: string): boolean {
  const lines = diff.split('\n');
  const changed = lines.filter(
    l => (l.startsWith('+') || l.startsWith('-')) && !l.startsWith('+++') && !l.startsWith('---')
  );
  return changed.length >= 5;
}
```

Passed into `buildUserContent()`. When false, the body instruction is omitted from the prompt entirely.

### Default prompt changes (`buildUserContent`)

Add to the `RULES` block, conditionally when `hasSufficientSubstance` is true:

```
- Body (required):
  • 2–5 bullet points starting with "- "
  • Reference specific function/variable names in backticks where relevant
  • Explain what changed and why, not how
  • Separate from header with a blank line
```

Append a one-shot example before `OUTPUT ONLY THE COMMIT MESSAGE:`:

```
EXAMPLE OUTPUT:
fix(auth): handle insufficient_role case in route middleware

- Added `insufficient_role` to `auth.failure` metrics for privilege failures
- Updated `routePatternOrSentinel` to use route templates instead of resolved paths
- Adjusted tests to reflect new metric attributes and fallback behavior
```

### Custom-rules path fix

`buildRulesSection()` currently only emits a `BODY:` section when `bodyMaxLineLength` is set. Body requirement should be emitted unconditionally; `bodyMaxLineLength` becomes an additive constraint, not the trigger.

### Files changed
- `packages/ai-worker/src/index.ts` — `buildUserContent()`, `buildRulesSection()`, new `hasSufficientSubstance()`

## Feature 2 — Commitlint Config Detection

### Goal
When `qc` is run in a repo with a commitlint config, detect and apply those rules automatically. Commitlint config overrides the user's global `~/.config/qc/config.json` rules, but team rules from the API still win.

### Rule priority (low → high)
```
commitlint config → local config (config.rules) → team rules (API)
```

### New file: `packages/cli/src/commitlint.ts`

**Config file search order** (checked in git root, first match wins):
```
commitlint.config.mjs
commitlint.config.js
commitlint.config.cjs
commitlint.config.ts
.commitlintrc.json
.commitlintrc
.commitlintrc.yml
.commitlintrc.yaml
.commitlintrc.js
.commitlintrc.mjs
```

**Evaluation strategy** (three-stage with silent fallback):

1. **`npx --no commitlint --print-config`** — runs commitlint's own resolver, returns fully-resolved JSON. Used when commitlint is installed in the project. `--no` prevents npm from auto-installing.
2. **Inline `node --input-type=module` evaluation** — spawns a small inline script that dynamically imports the config and `JSON.stringify`s the default export. Works for `.mjs`/`.js` without commitlint installed.
3. **YAML parse** — for `.commitlintrc.yml` and `.commitlintrc.yaml` via the `yaml` npm package (added as a `dependencies` entry in `packages/cli`).
4. **Direct JSON parse** — for `.commitlintrc.json` and `.commitlintrc`.
5. **Silent return `undefined`** if all strategies fail — never throws, never blocks a commit.

**Commitlint rule tuple → `CommitRules` mapping:**

Commitlint rules are `[severity, applicability, value]`. Only map rules where severity ≥ 1 and applicability is `'always'`, **except `subject-full-stop`** which uses `applicability: 'never'` (the standard commitlint convention meaning "subject must not end with this character").

| Commitlint rule | `CommitRules` field |
|---|---|
| `type-enum` | `types` |
| `scope-enum` | `scopes` |
| `header-max-length` | `headerMaxLength` |
| `subject-max-length` | `subjectMaxLength` |
| `body-max-line-length` | `bodyMaxLineLength` |
| `type-case` | `typeCase` |
| `scope-case` | `scopeCase` |
| `subject-case` | `subjectCase` |
| `subject-full-stop` | `subjectFullStop` |

**Integration in `packages/cli/src/index.ts` — `runCommit()`:**

```ts
const commitlintRules = await detectCommitlintRules();
let rules = { ...commitlintRules, ...(config.rules ?? {}) };
// team rules applied later still win: rules = { ...rules, ...teamRules }
```

`detectCommitlintRules()` also called in `packages/cli/src/commands/pr.ts` and passed in `PRRequest.rules`, so PR descriptions respect the same type/scope conventions as commits.

### Files changed
- `packages/cli/src/commitlint.ts` — new file
- `packages/cli/src/index.ts` — `runCommit()`, integrate `detectCommitlintRules()`
- `packages/cli/src/commands/pr.ts` — pass commitlint rules in `PRRequest`

## Feature 3 — PR Title Generation

### Goal
`qc pr` outputs a distinct PR title separate from the body. `qc pr --create` uses it directly for `gh pr create --title` instead of naively grabbing the first line of the body.

### AI output format

`buildPRUserContent()` gains `TITLE:` as the first line of `OUTPUT FORMAT`:

```
OUTPUT FORMAT:
TITLE: <imperative one-line PR title, max 72 chars, no period>

## Summary
<1-3 sentence overview>

## Changes
- <grouped by area, bullet points>

## Testing
- <suggested test steps>
```

### Title extraction in ai-worker route handler

```ts
const raw = data.pr?.response ?? '';
const titleMatch = raw.match(/^TITLE:\s*(.+)/m);
const body = raw.replace(/^TITLE:[^\n]*\n?/, '').trim();
// Fallback: if AI omits TITLE: line, use first non-empty line of body (preserves --create behavior)
const title = titleMatch?.[1]?.trim() ?? body.split('\n').find(l => l.trim()) ?? '';
return { pr: { title, response: body } };
```

### Type changes (`packages/shared/src/types.ts`)

```ts
// Before
export interface PRWorkerResponse {
  pr: { response: string };
}

// After
export interface PRWorkerResponse {
  pr: { title: string; response: string };
}
```

Gateway response gains `title` field (backward-compatible — existing callers ignore it).

### API client (`packages/cli/src/api.ts`)

`generatePR()` returns `{ message: string; title: string }`.

### CLI output (`packages/cli/src/commands/pr.ts`)

```
Title: <title>

<body>
```

`--create` uses title directly: `gh pr create --title title --body result.message`.

### Files changed
- `packages/shared/src/types.ts` — extend `PRWorkerResponse`
- `packages/ai-worker/src/index.ts` — `buildPRUserContent()`, title extraction in handler
- `packages/api-gateway/src/routes/pr.ts` — forward `title` in response
- `packages/cli/src/api.ts` — `generatePR()` return type
- `packages/cli/src/commands/pr.ts` — display + `--create` usage

## Feature 4 — PR Template Support

### Goal
When a repo has a `.github/pull_request_template.md`, `qc pr` uses it as the strict output structure. The AI fills in content, selects checkboxes, and preserves process checklists — all determined by analyzing the template's structure, not by hardcoded section names.

### Template detection (`packages/cli/src/commands/pr.ts`)

Check in git root, first match wins:
```
.github/pull_request_template.md
.github/PULL_REQUEST_TEMPLATE.md
pull_request_template.md
```

Read content, cap at 16KB. Log to stderr: `[qc] Using PR template from .github/pull_request_template.md`.

### Type changes (`packages/shared/src/types.ts`)

```ts
export interface PRRequest {
  commits: string[];
  diff_stat: string;
  base_branch: string;
  current_branch?: string;   // new — for checkbox selector context
  pr_template?: string;      // new
  rules?: CommitRules;
  model?: string;
}
```

`current_branch` is populated via `getCurrentBranch()` (already in `git.ts`).

### Gateway validation (`packages/api-gateway/src/routes/pr.ts`)

Accept `pr_template` (string, max 16KB) and `current_branch` (string). Validate and forward to ai-worker.

### Prompt instruction (`packages/ai-worker/src/index.ts` — `buildPRUserContent()`)

When `pr_template` is present, replace the hardcoded `OUTPUT FORMAT` block with pattern-based structural rules — no section names hardcoded:

```
STRICT PR TEMPLATE — reproduce the full template below with these structural rules applied.
Analyze each section's content to determine how to handle it:

1. SELECTOR sections — contain mutually exclusive `- [ ]` options describing categories
   (e.g. PR type, change type): check the single best-matching option based on the commits
   and branch name. Leave others unchecked.

2. GUIDANCE sections — contain bullet points written as instructions or policies
   (imperative language, "should", "do not", naming conventions): copy verbatim, unchanged.

3. FILL-IN sections — contain empty bullets (`- ` with no content) or `<angle-bracket
   placeholders>`: replace with content generated from the commits.

4. REFERENCE sections — contain link/ticket patterns with `N/A` fallbacks
   (issue numbers, Linear IDs, project items): extract from commit messages where possible,
   otherwise use N/A.

5. PROCESS CHECKLIST sections — contain `- [ ]` items phrased as verification steps
   ("tests added", "CI passes", "reviewed", "updated"): leave ALL boxes unchecked.
   These are for the human author to complete after the PR is opened.

Keep all headings exactly as written. Do not add or remove sections.

CURRENT BRANCH: <current_branch>
BASE BRANCH: <base_branch>

TEMPLATE:
<pr_template content>
```

When no template is present, the existing `## Summary / ## Changes / ## Testing` format is used unchanged.

### Files changed
- `packages/shared/src/types.ts` — `PRRequest` gains `pr_template`, `current_branch`
- `packages/cli/src/commands/pr.ts` — template detection, `current_branch` population
- `packages/cli/src/api.ts` — pass new fields to API
- `packages/api-gateway/src/routes/pr.ts` — accept, validate, forward new fields
- `packages/ai-worker/src/index.ts` — `buildPRUserContent()` template path
